CPMAI-D5-001 Production monitoring and performance trackingMEDIUM Answer: B

A project manager is defining what the monitoring for a demand forecasting model should report each week. The team proposes reporting the average size of the forecast error. The business plans staffing from the forecast and is affected differently by under-forecasting than by over-forecasting. What should the report add?

  1. AThe number of forecasts produced during the week, so the error can be put in context
  2. BThe direction of the errors alongside their size
  3. CThe largest single forecast error observed during the week
  4. DThe average error from the previous week, so the trend can be seen
Key ideaWhere two directions of error have different consequences, a single magnitude conceals which occurred.
AVolume gives scale to the reporting period. It does not distinguish the two kinds of error the business experiences differently.
BAn average magnitude treats a forecast that is too low the same as one that is too high. The business is affected differently by each, so the direction has to be visible.
CA worst case is useful for understanding exposure and is worth including. On its own it still does not show which direction the errors ran.
DA trend line on the same measure inherits the same limitation in both periods.
CPMAI-D5-002 Deployment planning and release strategyMEDIUM Answer: A

A model that passed evaluation is ready to go live for all branches at once. The project manager proposes releasing it to a small number of branches first. The team argues that evaluation already showed the model works and that a staged release only delays the benefit. What does the staged release provide that evaluation did not?

  1. AEvidence of how the model behaves within the live process, at limited exposure
  2. BAnother measurement on the same held-out evaluation records before wider release
  3. CAn opportunity to collect more training records before the model reaches every branch
  4. DAssurance that the model's infrastructure can carry the full production load
Key ideaEvaluation measures the model; a staged release measures the model inside the live process around it.
AEvaluation scored predictions against held-out records. A staged release exercises the integrations, the handoffs and the people acting on the output, with a small population carrying any problems.
BRe-running the original evaluation repeats a measurement already taken on records the model has already been scored against. It exercises none of the live process around the model.
CRecords gathered during a staged release can be useful later. Gathering them is not the reason to limit exposure at go-live.
DLoad behaviour at a few branches says little about full volume, so a staged release is weak evidence for capacity. Capacity is tested separately.
CPMAI-D5-003 Drift detection and retrainingMEDIUM Answer: D

A project manager asks what should happen when monitoring signals that a live model's performance has fallen below the agreed level. The team says it would investigate and decide at the time. The model supports decisions that continue to be made while any investigation proceeds. What should be agreed in advance?

  1. AThe maximum time the investigation is permitted to take before it must conclude
  2. BWhich team member will carry out the investigation when the signal is raised
  3. CThe level at which the monitoring signal should be set for the model
  4. DWhat happens to live decisions while the investigation runs, and who decides
Key ideaA response agreed before an incident removes the need to negotiate one while decisions continue.
AA time limit adds pressure without saying what happens to decisions during the period. It also cannot force a diagnosis to arrive.
BNaming an investigator is a useful part of the response plan. It does not settle what happens to the decisions being made meanwhile.
CThe trigger level is already agreed in the scenario. What is missing is the response once it fires.
DDecisions do not pause for an investigation. Agreeing beforehand whether the model keeps serving, falls back or routes to people prevents that being argued while the exposure continues.
CPMAI-D5-004 Incident response, rollback and failure handlingMEDIUM Answer: B,D

A project manager is writing the incident procedure for a live model that supports customer-facing decisions. The team has already covered how to diagnose a fault and how to deploy a fix. Which further elements should the procedure define? Select two.

  1. AWhich algorithm the replacement model should use if the fault cannot be corrected
  2. BHow live decisions are handled while the fault is being investigated
  3. CThe budget available for additional infrastructure during the incident
  4. DWho informs the affected users and what they are told
  5. EThe format in which the post-incident report should be written
Key ideaAn incident procedure covers stopping the harm and telling the people affected, not only repairing the system.
AChoosing a modelling approach is development work that follows a diagnosis. It does not belong in the immediate response.
BDecisions continue throughout an investigation. Deciding beforehand whether the model keeps serving, falls back or routes to people is what limits the exposure.
CSpending authority may matter for a capacity incident. It is not a general element of a model incident procedure.
DPeople acting on the output need to know its status. Without a defined route the information reaches them late or not at all.
EA report template is useful afterwards and contributes nothing during the response.
CPMAI-D5-005 Adoption, training and change managementMEDIUM Answer: A,C

A model has been live for a month and adoption is lower than planned. Production monitoring confirms the model is meeting its agreed performance level. The project manager wants to understand why adoption is low before proposing any change. Which two sources of evidence should be gathered first? Select two.

  1. AUsage data showing where in the process people stop engaging with the output
  2. BThe model's accuracy figures over the month since it went live
  3. CDirect accounts from the staff expected to use it
  4. DA comparison with adoption rates reported by other organisations
  5. EThe volume of records the model processed during the month
Key ideaDiagnosing low adoption needs both what people are doing and why they are doing it.
AThe point at which engagement drops narrows the possible causes quickly, and separates people who do not open the output at all from those who open it and disregard it.
BThe monitoring already confirms the model is meeting its agreed level, so performance is not the open question. A model performing to target can still go unused.
CUsage data shows the pattern and not the reason. Only the people doing the work can say what stops them acting on the output.
DAnother organisation's rate reflects its own process, staff and tool, and cannot explain the pattern here.
EProcessing volume describes the service running, not whether anyone acted on what it produced.
CPMAI-D5-006 Integration with business processes and systemsEASY Answer: B

A model produces a risk score for each incoming application. During design the team assumed a reviewer would read the score before deciding. In the live process, the score arrives in a queue the reviewer works through after the decision has been recorded. What should the project manager conclude?

  1. AThe reviewer should be instructed to revisit decisions where the score later proves high
  2. BThe model cannot affect the decisions it was built to support until it is delivered before them
  3. CThe score should be recalculated at the moment the reviewer opens the queue item
  4. DThe model's accuracy should be improved so that high scores are easier for reviewers to notice
Key ideaA prediction delivered after the decision point cannot influence the decision it was built to inform.
AReworking recorded decisions is costly and does not deliver the intended benefit, which was a better decision the first time.
BA correct score arriving after the decision is recorded changes nothing. The integration has to place the output at the point where the decision is actually made.
CRecalculating does not move the delivery earlier. The score would still arrive after the decision was recorded.
DNo level of accuracy compensates for arriving too late to inform the decision.
CPMAI-D5-007 Human oversight and escalation in operationHARD Answer: A

A model screens applications and a reviewer confirms each decision before it takes effect. After six months the reviewer confirms almost every decision without change, and the time spent per case has fallen steadily. The project manager is told the human check is therefore working well. What should be examined?

  1. AWhether the reviewer is still examining each case or has come to accept the model's output by default
  2. BWhether the reviewer has enough cases each day to maintain familiarity with the process
  3. CWhether the model's accuracy has improved over the six months of operation
  4. DWhether a second reviewer should be added to confirm the first reviewer's decisions
Key ideaA review step that approves everything may no longer be exercising independent judgement.
AA near-total confirmation rate with falling review time is consistent with genuine agreement and also with the check becoming a formality. Which of the two it is determines whether the control exists.
BVolume affects familiarity and is worth knowing. It does not establish whether the cases are being examined.
CImproving accuracy would explain fewer corrections and would not show whether the check still functions.
DAdding a layer multiplies the cost and can dilute responsibility. It does not diagnose the existing check.
CPMAI-D5-008 Model lifecycle, versioning and retirementMEDIUM Answer: D

Three versions of a model have been deployed over a year. The team can identify which version is running now but cannot say which version produced a given past decision, because the outputs were stored without a version marker. A customer queries a decision made eight months ago. What difficulty does this create?

  1. AThe current model cannot be used to re-score the customer's case for comparison
  2. BThe team cannot establish whether the model has improved over the three versions
  3. CThe customer's case will need to be decided again from the beginning
  4. DThe decision cannot be traced to the logic that produced it
Key ideaA decision cannot be explained after the fact unless the version that produced it is recorded with it.
ARe-scoring with the current model is straightforward and would answer a different question, since that version may not be the one that decided.
BComparing versions is a real difficulty here. The pressing issue is explaining one decision to the customer who queried it.
CRe-deciding may follow. It does not explain the original decision, which is what was asked.
DExplaining the decision requires knowing which model made it. Without the marker, the team can only guess which of three versions was live and what it would have done.
CPMAI-D5-009 Operational governance and value realisationHARD Answer: C

A live model's monthly running cost has risen steadily as usage has grown, and now exceeds the saving the business case attributed to it. The model is accurate and well adopted. The project manager is asked what should happen. What is the appropriate response?

  1. AContinue, since the model is accurate and staff have adopted it successfully
  2. BReduce the model's usage until the running cost falls back within the original saving
  3. CReview whether the cost can be reduced or the benefit increased, and decide on the result
  4. DRecalculate the original business case using the current cost figures
Key ideaAn operating model has to keep earning its cost, and that balance can change after deployment.
AAccuracy and adoption are means to a benefit. Neither justifies an arrangement that now costs more than it returns.
BCutting usage indiscriminately removes benefit alongside cost, and may remove the most valuable uses first.
CA model that costs more than it returns is not worth running as configured. Options include cheaper serving, narrowing its use to the cases with most value, or accepting it is no longer viable.
DRestating the case documents the position. It does not decide what to do about it.
CPMAI-D5-010 Production monitoring and performance trackingHARD Answer: C

A team reports a single monthly accuracy figure for a model that serves five customer segments of very different sizes. The figure has been stable for six months. The project manager asks whether that stability is sufficient assurance. What is the limitation of the report as it stands?

  1. AA monthly reporting interval is too infrequent to detect a problem in a live model
  2. BAccuracy is the wrong measure to report for a model serving customer segments
  3. CA stable total can hide a decline in one segment offset by others
  4. DSix months is not long enough to establish that a model's performance is stable
Key ideaOne pooled figure can stay steady while performance moves in opposite directions underneath it.
AReporting frequency is a separate question worth reviewing. A more frequent pooled figure would conceal the same thing.
BAccuracy may or may not be the best measure here, but the defect described is the pooling, which would affect any measure reported the same way.
CThe pooled figure is weighted towards the larger segments. A serious fall in a smaller segment can be absorbed without the reported number moving.
DA longer run of the same pooled figure inherits the same blind spot.
CPMAI-D5-011 Deployment planning and release strategyMEDIUM Answer: D

A model will be released to a group of users while the remaining users continue on the existing process. The team proposes choosing the first group from one region, because that region's manager is enthusiastic about the change. What should the project manager weigh against that convenience?

  1. AWhether the other regions will object to not being included in the first release group
  2. BWhether that region has enough users to complete the release within the planned window
  3. CWhether that region's manager can take responsibility for the model's outputs
  4. DWhether that region's cases represent the conditions the model will meet elsewhere
Key ideaA first release group is chosen for what its results will tell you, not for who volunteered.
AManaging expectations across regions is a real communication task. It does not affect what the first group's results will tell the project.
BGroup size affects how quickly evidence accumulates. Representativeness determines whether the evidence means anything.
CAccountability for outputs sits with the organisation operating the model, not with whoever hosts the first release.
DAn enthusiastic group is easier to work with, and a region with atypical cases produces results that do not carry to the rest. The group has to be informative as well as willing.
CPMAI-D5-012 Drift detection and retrainingHARD Answer: A

Monitoring shows that the mix of incoming records for a live model has shifted markedly over six weeks, although the model's measured accuracy has not yet moved. The team proposes taking no action until accuracy declines. What is the argument for acting on the input shift before then?

  1. AOutcomes arrive after the decisions are made, so waiting may expose live decisions before any performance effect becomes observable
  2. BAn input shift always causes a fall in accuracy, so the decline is certain to follow
  3. CThe measured accuracy figure is unreliable whenever the input mix has changed
  4. DRetraining is cheaper to perform before a decline appears than after one
Key ideaA shift in inputs can precede a performance effect that outcome data will only reveal later.
AThe input shift is observable now; any accuracy effect becomes measurable only once outcomes for the new mix are known. Waiting concedes that interval to a change whose consequences are not yet visible.
BA model can be insensitive to a shift in fields it depends on weakly, so a decline is a risk rather than a certainty. The case for acting rests on the delay in observing it.
CThe figure remains a valid measurement of the records it covers. The issue is what it cannot yet cover, not that it is wrong.
DCost may well be similar either way, and the reason to act early is exposure during the delay rather than the price of the work.
CPMAI-D5-013 Incident response, rollback and failure handlingMEDIUM Answer: B

A model's upstream data feed fails and delivers no records. The model has no defined behaviour for that case and returns its default output for every request. Downstream systems accept the results as normal. The project manager is asked what should have been in place. What is the answer?

  1. AA second data feed that can be used whenever the first one fails
  2. BA behaviour that makes the failure visible rather than returning ordinary-looking output
  3. CAn alert sent to the data team whenever the upstream feed stops delivering records
  4. DA larger cache of recent records that the model can fall back on
Key ideaA system should fail visibly rather than continue producing output that looks ordinary.
AA redundant feed reduces how often the situation arises and is worth considering on cost grounds. If both fail, the silent default behaviour returns.
BSilent default output is indistinguishable from real predictions, so the failure propagates unnoticed. Stopping, or marking the output as unavailable, keeps the fault detectable.
CAlerting the data team is necessary and addresses the feed. The model would still be serving default output downstream in the meantime.
DServing from a cache substitutes stale predictions for absent ones, which is a decision to take deliberately rather than a default.
CPMAI-D5-014 Adoption, training and change managementMEDIUM Answer: B

A model's design is agreed and the build is complete. Two weeks before go-live the project manager reviews the transition plan, which covers training on the new screen and the cutover date. Experienced staff point out several case types they handle today for which the new workflow has no route. What should the project manager settle before go-live?

  1. AProceed as planned and add routes for those case types in a later release
  2. BHow those case types will be handled in the live workflow from the cutover
  3. CExtended training, so staff understand that the model does not cover those case types
  4. DAn entry in the project risk log, to be reviewed once the model is operating
Key ideaA live workflow needs a defined route for every case that will arrive, not only the ones the model handles.
AThose cases arrive from the cutover onwards, so deferring the route leaves them unhandled through the period when the transition is most fragile.
BThe cases will arrive whether or not a route exists. Agreeing where they go, and who handles them, is what allows the workflow to operate from day one.
CKnowing the gap exists does not give staff anywhere to send the cases. Awareness is not a route.
DA risk entry records the gap without resolving it, and the cases still arrive on the cutover date.
CPMAI-D5-015 Integration with business processes and systemsMEDIUM Answer: A

A model is scheduled to run overnight and write its results before the business day begins. The upstream extract it depends on sometimes completes late. The team has not defined what the model should do when the extract is unavailable at its scheduled run time. What should be decided in advance?

  1. AWhether the model waits, runs on the previous extract, or produces nothing, and how users are told
  2. BWhether the upstream extract can be guaranteed to complete before the model runs
  3. CWhether the model's scheduled run time can be moved later into the night
  4. DWhether the results from the previous day can be retained for longer in the system
Key ideaA dependency that can be late needs a defined behaviour before it is late for the first time.
AEach option has a different consequence for the business day. Choosing at the time, under pressure, risks stale results being presented as current with nobody aware.
BSuch a guarantee is worth pursuing with the upstream owner and cannot be relied on absolutely. A defined behaviour is still needed for the occasions it fails.
CA later slot reduces how often the conflict occurs without removing it. The behaviour on failure is still undefined.
DRetention decides what remains available. It does not decide what the model does or what users are told.
CPMAI-D5-016 Human oversight and escalation in operationMEDIUM Answer: C

Operational staff can override a live model's recommendation. Over the first quarter, overrides are recorded as a simple count with no reason captured. The count is rising. The project manager wants to understand what the rise means. What should be changed in how overrides are handled?

  1. ARequire approval from a supervisor before an override can be recorded
  2. BRemove the override facility, since a rising count suggests it is being misused
  3. CCapture the reason for each override, so the pattern behind the rise can be seen
  4. DCompare the override count with the count recorded by a similar organisation
Key ideaAn override is evidence about the model, but only if the reason for it is captured.
AAn approval step suppresses overrides rather than explaining them, and may discourage staff from correcting the model at all.
BNothing indicates misuse, and removing the facility would leave staff unable to correct a wrong recommendation.
CA rising count is consistent with a degrading model, a shift in cases, or growing confidence among staff in exercising judgement. Without reasons the three are indistinguishable.
DAnother organisation's rate reflects its own model, cases and staff. It cannot explain the pattern here.
CPMAI-D5-017 Model lifecycle, versioning and retirementHARD Answer: D

A model is due to be replaced by a new version built by a different vendor.   1. AThe training code, so that the previous model can be rebuilt if the new one underperforms
  2. BThe monitoring dashboards, so the two models' performance can be compared over time
  3. CThe vendor contract for the current model, in case the replacement has to be reversed
  4. DThe prediction and monitoring history together with the model's documented limits, since past operation and decisions may still need to be examined

AKeeping the code is reasonable insurance for continuity. It does not preserve the record of what was decided and why.

CContract retention is a procurement matter governed by its own rules and unrelated to explaining past decisions.
DDecommissioning removes the ability to show what the model decided and how it behaved while operating. Both can be raised long after it stops running, so the records have to outlive the environment.
CPMAI-D5-018 Operational governance and value realisationMEDIUM Answer: A

A model operating in production is owned by the team that built it. That team is being disbanded at the end of the quarter and its members reassigned across the organisation. The model will continue to run. The project manager is asked what must be settled before the team disperses. What is the priority?

  1. AWho owns the model in operation once the team no longer exists
  2. BThat the team documents how the model was built before its members disperse
  3. CThat the model's code is moved into a repository the organisation controls centrally
  4. DThat the team's members remain available to answer questions for a handover period
Key ideaA model in production needs a named owner for as long as it runs, independent of the team that built it.
AMonitoring, incidents, retraining and retirement all need somebody accountable. Without a transfer of ownership the model runs with nobody answering for it.
BDocumentation supports whoever takes over and is worth capturing. It does not appoint anyone to act on it.
CCentral storage protects the artefact. It does not make anyone responsible for the running service.
DA handover period helps a transfer that has been arranged. It is not a substitute for naming an owner.
CPMAI-D5-019 Production monitoring and performance trackingMEDIUM Answer: C,E

  2. BThe version of the software library the model was trained with
  3. CWhether the incoming data still resembles the data the model was built on
  4. DThe total time the team spent on model-related work during the week
  5. EWhether the outcomes the model was meant to improve are moving as expected
Key ideaOperational monitoring covers both what the model receives and what results from what it produces.
AVolume describes activity and is useful for capacity planning. It says nothing about whether predictions are sound or useful.
BThe library version belongs in deployment records. It is fixed between releases and is not a weekly operational measure.
CThe model was fitted to a particular kind of input. A shift in what arrives is a leading indicator of degraded predictions, and it is visible immediately.
DEffort is a project management measure. It does not indicate how the model is behaving in production.
EThe model was deployed to change a business result. Tracking that result is what shows the deployment is delivering, rather than merely operating.

CPMAI-D5-021 Drift detection and retrainingMEDIUM Answer: D

The project manager asks what the schedule is based on and is told it was chosen because monthly is convenient for the team's release calendar. What should the project manager establish instead?

  1. AWhether the team has capacity to retrain more frequently than once a month
  2. BWhether a monthly cycle matches the retraining cadence used by comparable organisations
  3. CWhether monthly retraining will produce a measurable accuracy gain each time it runs
  4. DHow quickly the conditions the model depends on actually change, and what the monitoring shows
Key ideaA retraining cadence should follow how quickly the conditions change, not the release calendar.
